Scope inspected:
- `v2/backend/app`
- `v2/backend/tests`
- `claude_worklog/phase2_core_rebuild/paper_mode_impl`

Result: BLOCKED.

## Summary

The paper-mode flag surface itself is clean: `PaperModeFlag` only accepts `paper` and `live_blocked`, always requires `live_blocked is True`, and the service rejects `live` / `live_enabled` requested modes. The 2J.C composition root is a pure clock-capturing binder and does not introduce Redis, HTTP, FastAPI, exchange, or live execution behavior.

The blocker is integration-level. The current typed risk gateway and typed paper ledger can still be assembled without any `PaperModeFlag` input, and their records do not carry `paper_mode_mode`, `paper_mode_live_blocked`, or `paper_mode_flag_emitted_ts_ms`. Paper-mode evidence exists in harnesses beside the risk/ledger records, but it is not enforced by the typed risk gateway or ledger boundary. That fails the review checks for paper ledger integration, risk gateway enforcement, and decision explainability as an MVP-level paper-mode guarantee.

## Checks

### Paper mode flag composition

PASS, local surface only.

Evidence:
- `v2/backend/app/domain/paper_mode/flag.py` defines `PAPER_MODE_PAPER = "paper"` and `PAPER_MODE_LIVE_BLOCKED = "live_blocked"` only.
- `PaperModeFlag.__post_init__` rejects unknown modes, negative/non-int timestamps, and any `live_blocked` value other than `True`.
- `v2/backend/app/services/paper_mode/service.py` accepts only `{paper, live_blocked}`, rejects `live` and `live_enabled`, calls the injected clock once, and constructs the flag with `live_blocked=True`.
- `v2/backend/app/composition/paper_mode/runtime.py` exposes `build_paper_mode_runtime(now_ms_clock=...)` and a `paper_mode_now(requested_mode=...)` closure without touching Redis, HTTP, FastAPI, files, or exchange APIs.

### No live execution

PASS for the inspected paper-mode typed MVP surfaces.

Evidence:
- `v2/backend/app/services/execution_router.py` is a placeholder stating live order calls raise `LiveBlockedError` until a later milestone.
- `v2/backend/app/domain/orchestrator_decision/record.py`, `v2/backend/app/domain/risk_gateway/record.py`, and `v2/backend/app/domain/paper_execution_ledger/record.py` all require `live_blocked is True`.
- The paper-mode 2J implementation artifacts report no Redis, exchange mutation, live service restart, leverage/margin change, deployment, or secret exposure.

Note: `v2/backend/app/cli/paper_online_runtime.py` contains a separate dict-based paper runtime that writes local/public V2 artifacts and simulates paper fill economics, but the inspected code path marks `exchange_order_allowed=False`, `exchange_orders=False`, `live_order=False`, and `legacy_redis_write=False`. I did not run this CLI.

### Paper ledger integration

BLOCKED.

Evidence:
- `v2/backend/app/services/paper_execution_ledger/service.py::assemble_paper_execution_ledger_entry` accepts only `decision: RiskDecisionRecord` and `now_ms_clock`.
- `v2/backend/app/composition/paper_execution_ledger/runtime.py::build_paper_execution_ledger_recorder` captures only `now_ms_clock`.
- `v2/backend/app/domain/paper_execution_ledger/record.py::PaperExecutionLedgerEntry` has no paper-mode fields. It records `live_blocked=True`, but not which paper-mode flag authorized the paper-only posture.
- Harnesses such as `v2/backend/tests/unit/paper_mode_evidence_collection_harness/harness.py` emit a `PaperModeFlag` and then independently assemble replay evidence from already-built ledger entries. The flag is not an input to the ledger recorder.

Impact: a caller can create a valid `PaperExecutionLedgerEntry` from a valid `RiskDecisionRecord` without presenting a current paper-mode flag.

### Risk gateway enforcement

BLOCKED.

Evidence:
- `v2/backend/app/services/risk_gateway/service.py::assemble_risk_decision_record` accepts only `decision: OrchestratorDecisionRecord` and `now_ms_clock`.
- `v2/backend/app/composition/risk_gateway/runtime.py::build_risk_decision_evaluator` captures only `now_ms_clock`.
- `v2/backend/app/domain/risk_gateway/record.py::RiskDecisionRecord` has no paper-mode fields and no relationship to `PaperModeFlag`.
- The risk gateway hard-codes `live_blocked=True`, which is a useful invariant, but it does not prove that the risk decision was gated by the runtime paper-mode flag at decision time.

Impact: risk decisions can be allowed for `open_long` / `open_short` without any paper-mode flag being supplied or checked.

### Decision explainability

BLOCKED.

Evidence:
- `v2/backend/tests/unit/decision_explainability_data_contract/harness.py` projects `paper_mode_live_blocked` and `paper_mode_mode` into an explainability envelope, but it does so by joining a harness-level `PaperModeFlag` beside fixture `RiskDecisionRecord` values.
- The typed `RiskDecisionRecord` and `PaperExecutionLedgerEntry` records do not themselves carry paper-mode evidence.
- There is no typed enforcement that the explainability envelope's paper-mode fields came from the same decision-time flow as the risk/ledger record.

Impact: explainability tests prove a projection can include paper-mode fields, but not that production decision records are inseparable from paper-mode posture.

## Concrete Blockers

1. Risk gateway does not require paper-mode evidence.
   - `assemble_risk_decision_record(...)` and `build_risk_decision_evaluator(...)` can emit valid allow/deny records with no `PaperModeFlag`.

2. Paper execution ledger does not require paper-mode evidence.
   - `assemble_paper_execution_ledger_entry(...)` and `build_paper_execution_ledger_recorder(...)` can emit valid ledger records with no `PaperModeFlag`.

3. Typed risk and ledger records do not carry paper-mode explainability fields.
   - There is no `paper_mode_mode`, `paper_mode_live_blocked`, or `paper_mode_flag_emitted_ts_ms` on `RiskDecisionRecord` or `PaperExecutionLedgerEntry`.

4. Explainability currently relies on harness-side joining.
   - Tests show paper-mode data can be projected beside risk decisions, but not that risk/ledger assembly enforces or preserves that evidence.
