# Codex Parallel Read-Only Review

Verdict: BLOCKED for dashboard integration readiness. READY only as a documentation/specification packet.

Scope honored: read-only review only. No source patching, no dirty-work changes, no legacy-directory access, no Redis writes, no service restarts, no order actions, and no live-trading changes.

Findings:
1. Paper/backtest MVP compatibility is partial. The underlying non-live proof rows preserve five scenarios, one allow/four block outcomes, paper ledger evidence, replay counts, and `blocked_human_only` live-gate posture. That is compatible with paper/backtest evidence review, but the committed 069C milestone does not materialize the dashboard payload contract it defines.
2. Existing dashboard/public payloads do not expose the 069C envelope. The reviewed payloads lack `lineage_contract_version`, `payload_status`, `warning_count`, `payload_warnings`, `lineage_rows`, and per-row `lineage_authority`. One public lineage payload is a dispatch/status summary rather than the operator lineage table described by 069C.
3. The current cockpit lineage row presents a concrete-looking `signal_id` value derived from an existing decision identifier, while 069B/069C require `signal_id` to remain `null` or visibly scaffold-only until a concrete signal domain producer exists. This can mislead operators by treating a known gap as an ID-bearing lineage stage.
4. Risk-gateway handoff remains incomplete for operator explainability. The service-level risk domain only maps orchestrator allow/deny categories, while proof/dashboard reasons include richer stale-data, duplicate-signal, hedge-residual, and short-squeeze explanations. 069C correctly asks for `RISK_REASON_MAPPING_NOT_DOMAIN_COMPLETE`, but no implemented payload warning was found.
5. Replay lineage remains incomplete in the proof/dashboard surface. Replay rows expose a run ID and scenario data but omit `replay_step_id`; 069C requires `replay_step_id: null` plus an explicit warning when source proof rows do not expose it. No implemented warning surface was found.
6. Paper trade lineage has a known derivation mismatch. The proof uses scenario-shaped `paper_*` IDs while the service derives `pt_` IDs from risk decisions. 069C requires a visible mismatch warning, but no implemented warning payload was found.
7. Fixture-only execution-intent and shadow IDs are not sufficiently distinguished in existing UI payloads. 069C requires those fields to be marked `fixture_only` with row warnings; existing rows expose the values without the required authority map.
8. Evidence freshness is stale for a promotion claim. The proof artifacts reviewed carry `generated_at` of 2026-05-08, while the milestone and review context are 2026-05-10. This does not invalidate the spec, but it should block implementation-readiness claims until the dashboard payload is regenerated and compared against the current committed sources.
9. Missing test-hardening recommendations: add a schema test for the 069C payload envelope; add row-level authority/warning tests for signal, execution intent, shadow, replay step, paper trade mismatch, and risk reason mapping; add a UI test that warnings are visible and filterable; add a no-inference test preventing missing IDs from scenario-name or prefix synthesis; add a freshness test comparing proof timestamps to the reviewed source commit window; add an exact marker-format test for GO/NO-GO files.

Conclusion: the committed milestone is a useful dashboard contract, but the review found no implemented payload or UI surface satisfying that contract. Treat 069C as contract-authored, not dashboard-integration-ready, until the payload builder, public artifact, UI rendering, and tests enforce the authority and warning model end to end.
